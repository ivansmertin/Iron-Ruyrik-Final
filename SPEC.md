Железный Рюрик — Product Specification
1. Что это за продукт

«Железный Рюрик» — небольшой частный спортивный зал в Великом Новгороде с ограниченной вместимостью.

Ключевая особенность:

посещение только по предварительной записи;
одновременно в зале может находиться не более 8 человек;
небольшое камерное пространство;
персональный подход;
два тренера с разной специализацией.

Тренеры:

Дима

триатлон;
бег;
трейлраннинг;
развитие выносливости;
подготовка к стартам.

Ваня

снижение веса;
рекомпозиция тела;
силовые тренировки;
набор мышечной массы;
общая физическая подготовка.

Приложение должно ощущаться не как приложение крупной федеральной сети, а как цифровая часть небольшого спортивного клуба.

Главные качества продукта:

простота → контроль → персональность → дисциплина.

2. Главная задача приложения

Основной пользовательский сценарий должен занимать несколько секунд:

Открыл приложение → увидел свободные места → выбрал время → записался.

Приложение решает четыре основные задачи:

запись в зал;
контроль загрузки зала;
взаимодействие с тренерами;
отслеживание собственного тренировочного прогресса.

Все остальные функции вторичны.

3. Платформа

На первом этапе разработать:

Mobile-first PWA

Приложение должно хорошо работать:

на iPhone;

Не строить отдельные native iOS/Android-приложения в MVP.

4. Роли

В системе три типа пользователей.

Клиент

Может:

зарегистрироваться;
записываться в зал;
отменять запись;
смотреть количество свободных мест;
выбирать тренера;
видеть свои тренировки;
отслеживать прогресс;
управлять профилем и абонементом.
Тренер

Получает возможности клиента плюс:

видеть свои тренировки;
видеть записанных клиентов;
просматривать клиентский профиль;
добавлять результаты;
оставлять заметки;
создавать индивидуальные тренировки.
Администратор

Может:

управлять расписанием;
управлять пользователями;
управлять тренерами;
блокировать время;
изменять вместимость;
видеть загрузку зала;
создавать и редактировать абонементы;
вручную записывать клиентов;
отменять записи;
просматривать статистику.

В MVP тренеры могут одновременно иметь права администратора.

5. Главная бизнес-логика
Вместимость

Максимальное количество людей, одновременно находящихся в зале:

8 человек.

Это жесткое ограничение.

Система никогда не должна позволять создать девятую пересекающуюся запись.

Это правило должно проверяться на backend, а не только интерфейсом.

7. Пересекающиеся записи

Нужно учитывать именно пересечение временных интервалов, а не просто количество записей с одинаковым временем начала.

Например:

Иван: 18:00–19:30
Сергей: 18:30–20:00

Оба человека находятся в зале с 18:30 до 19:30.

Алгоритм должен гарантировать:

concurrent_users <= 8

для любого момента времени.

Проверка должна быть транзакционной, чтобы два человека не смогли одновременно забронировать последнее место.

36. Recommended stack

Если проект создается с нуля:

Frontend
React
TypeScript
Vite
React Router
TanStack Query
UI

Собственная UI-система.

Можно использовать headless primitives, но внешний вид должен быть custom.

Не делать проект визуально похожим на стандартный shadcn dashboard.

Backend / database

Для MVP:

Self-hosted FastAPI
SQLAlchemy 2.x
Alembic
SQLite в WAL mode

Backend и database размещаются на собственном сервере. Сторонний BaaS не используется. Доступ к данным изолируется repository layer, чтобы при росте проекта SQLite можно было заменить на PostgreSQL без переписывания бизнес-логики и frontend API contracts.

Production authentication реализуется собственным backend в отдельной итерации. На Phase 2 разрешён только явно отделённый development auth с фиксированной server-side identity.

55. Критически важное требование к дизайну

Не создавать ощущение AI-generated interface.

Особенно избегать:

бессмысленных декоративных карточек;
случайных градиентов;
glow;
glassmorphism;
огромных маркетинговых заголовков внутри приложения;
декоративной статистики без функции;
случайных motivational slogans;
чрезмерного количества текста.

Каждый элемент должен выполнять функцию.

56. Brand personality

В интерфейсе должна ощущаться идея:

небольшой сильный зал, где тебя знают.

Не:

огромная фитнес-платформа.

Не:

приложение для бодибилдеров.

Не:

сервис бронирования.

Это прежде всего «Железный Рюрик», а запись — одна из его функций.

57. Ключевой UX-тест

Новый пользователь должен без объяснений понять:

где записаться;
сколько мест осталось;
когда его ближайшая тренировка;
кто его тренер;
сколько посещений осталось.

На получение любого из этих ответов должно уходить максимум несколько секунд.

59. Перед началом разработки

Codex должен:

изучить все изображения в текущей папке;
определить точные цвета бренда sampling'ом оригинальных изображений;
выбрать наиболее качественный исходник логотипа;
создать краткий DESIGN_SYSTEM.md;
создать IMPLEMENTATION_PLAN.md;
только после этого приступать к приложению.

Не изменять исходные изображения.

Не удалять файлы.

Не перезаписывать бренд-ассеты.

60. Definition of Done для первого прототипа

Прототип считается удачным, если:

приложение визуально однозначно относится к бренду «Железный Рюрик»;
интерфейс выглядит профессионально и современно;
нет ощущения шаблонного SaaS;
работает mobile и desktop;
можно пройти полный mock-flow записи;
заполненность 8 мест отображается понятно;
доступны страницы Димы и Вани;
есть профиль;
есть экран прогресса;
все основные состояния интерфейса существуют;
нет lorem ipsum;
нет вымышленных фактов;
русский язык естественный;
интерфейс можно использовать как основу production-приложения.
