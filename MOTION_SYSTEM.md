# Система Motion Design «Железный Рюрик»

> **Статус:** Активный стандарт системного motion design  
> **Платформа:** Mobile Web / Capacitor (iOS & Android)  
> **Концепция:** Непрерывный кинематографичный продуктовый интерфейс в эстетике атлетичной точности.

---

## 1. Философия и принципы

Система motion design «Железного Рюрика» опирается на принципы современных кинематографичных продуктовых интерфейсов (вдохновленных непрерывностью и пространственной связностью презентационных интерфейсов класса *GPT-6 Astra*), но строго адаптирована под **мобильное приложение частного спортивного зала**.

Это не промо-сайт и не витрина декоративных эффектов. В приложении полностью **исключены**:
- WebGL-фоны и 3D-модели;
- частицы, искры и генеративные сетки;
- искусственный скролл-джекинг;
- тяжелые фильтры `backdrop-filter: blur()`, анимируемые в рантайме;
- курсорные эффекты и декоративные свечения (glow).

### Ключевые принципы:
1. **Пространственная непрерывность (Spatial Continuity):** Экраны и состояния не сменяются через резкий монтаж (hard cut) или банальный fade-in/fade-out. Если объект существовал на предыдущем экране (например, карточка слота `18:00–19:00` или аватар тренера), он физически преобразуется в заголовок нового экрана.
2. **Атлетичная точность (Athletic Deceleration):** Никаких резиновых отскоков (bouncy spring) или мультяшных покачиваний. Движение имеет быстрый решительный старт и контролируемое, плотное торможение — как движение выверенного силового снаряда.
3. **Сборка данных (Assembly & Resolve):** Крупные числа, ключевые метрики и векторные графики не выпрыгивают статичным блоком, а динамически собираются в момент фокуса внимания, подчеркивая актуальность и физический прогресс атлета.
4. **Иерархия внимания:** Движение направляет взгляд на первичное действие (Primary CTA, подтверждение записи, выбор слота), а второстепенные элементы подстраиваются фоном.

## 2. Главное правило (Core Rule)

Любая анимация в приложении обязана отвечать минимум на **один** из 5 вопросов:

```
┌─────────────────────────────────────────────────────────────┐
│                      CORE MOTION RULE                       │
│                                                             │
│ 1. Откуда появился объект? (Пространственный источник)      │
│ 2. Куда он ушел?           (Направление завершения)         │
│ 3. Что изменилось?         (Дельта состояния, число, статус)│
│ 4. Что сейчас главное?     (Фокус внимания и следующий шаг) │
│ 5. Как два состояния       (Связь элементов между экранами) │
│    связаны между собой?                                     │
└─────────────────────────────────────────────────────────────┘
```

> **Правило фильтра:** Если анимация не отвечает ни на один из этих вопросов — она считается декоративным визуальным шумом и **не включается в код**.

## 3. Категории и тайминги (Duration Hierarchy)

В приложении действует строгая шкала продолжительности, исключающая одинаковые «усредненные» тайминги:

| Категория | Диапазон | Токен | Назначение |
| :--- | :--- | :--- | :--- |
| **A. MICRO** | 80–160ms | `--motion-duration-micro` (120ms)<br>`--motion-duration-micro-fast` (90ms) | Тап по кнопкам (`:active scale(0.97)`), выбор radio-кнопки формата тренировки, переключение чекбокса, смена иконки (шевроны, стрелки). |
| **B. UI STATE** | 160–260ms | `--motion-duration-ui` (220ms)<br>`--motion-duration-ui-fast` (180ms) | Переключение вкладок нижней навигации, фильтры даты в `DateStrip`, раскрытие шторки/аккордеона, заполнение сегментов загрузки зала (`CapacityIndicator`). |
| **C. PAGE / SHARED** | 260–420ms | `--motion-duration-page` (340ms)<br>`--motion-duration-page-fast` (280ms) | Переход между экранами через View Transitions API (слот → экран записи, карточка тренера → профиль тренера, модальные окна и шторки). |
| **D. REVEAL** | 300–600ms | `--motion-duration-reveal` (480ms)<br>`--motion-duration-reveal-fast` (380ms) | Редкие акцентные переходы: отрисовка линии SVG-графика веса, сборка hero-числа веса/посещений, экран успешного подтверждения тренировки. |

## 4. Кривые скорости (Easing Tokens)

Фирменный характер движения — **быстрый старт, мощный импульс и контролируемое торможение без отскока**.

```
  1.0 ┌─────────────────────────────┐
      │                      . . · ·│  <- Плавная, точная фиксация
      │                 . ·         │
      │             . ·             │
      │         . ·                 │
      │      . ·                    │
      │   .·                        │
      │ .·                          │  <- Решительный старт без задержки
  0.0 └─────────────────────────────┘
      0.0                         1.0
```

### Токены кривых:

1. `--motion-ease-standard: cubic-bezier(0.2, 0, 0, 1)`
   *Базовая кривая для большинства внутренних перемещений UI, смены цвета границ и микро-состояний.*
2. `--motion-ease-enter: cubic-bezier(0.05, 0.7, 0.1, 1)`
   *Появление элементов и входящие переходы. Объект входит в кадр быстро и стабильно фиксируется.*
3. `--motion-ease-exit: cubic-bezier(0.3, 0, 0.8, 0.15)`
   *Быстрый, чистый уход элементов без долгого затухания.*
4. `--motion-ease-emphasized: cubic-bezier(0.16, 1, 0.3, 1)`
   *Кинематографичная непрерывная кривая для Shared Transitions (View Transitions API) и сборки hero-метрик.*
5. `--motion-ease-direct: cubic-bezier(0.25, 1, 0.5, 1)`
   *Тактильный отклик прямого пальцевого нажатия (press down / release).*

## 6. Производительность (Mobile-First 60 FPS)

Мобильное приложение обязано гарантировать 60 кадров/сек на типичном Android-устройстве среднего класса.

### Жесткие правила реализации:
1. **Только Composite Properties:** Анимируются исключительно `transform` (включая `translate3d`, `scale`) и `opacity`.
2. **Запрет на анимацию геометрии:** Категорически запрещено анимировать `height`, `width`, `margin`, `padding`, `top`, `left`, `bottom`, `right`.
3. **Отказ от динамических blur:** Размытие (`backdrop-filter`) применяется только статически в шапке; переход сквозь анимируемые blur-фильтры в реальном времени вызывает сильные просадки GPU на мобильных устройствах.
4. **Изоляция слоев:** Для анимируемых контейнеров используется `will-change: transform, opacity;` только на время анимации с последующим сбросом.

## 7. Доступность (Accessibility & Reduced Motion)

Система поддерживает требования доступности WCAG 2.2 и системную настройку `prefers-reduced-motion: reduce`.

### Поведение при `prefers-reduced-motion: reduce`:
1. **Тайминги схлопываются до нуля:** Все CSS transitions и keyframe-анимации переключаются в `0.01ms`.
2. **Shared Transitions:** View Transitions отключают перемещения и трансформации масштабного слоя, подменяя их мгновенным отображением целевого экрана.
3. **Счетчики и графика:** Хук `useCountUp` мгновенно возвращает конечное значение без покадрового счетчика.
4. **SVG Графики:** Полилайн графика отображается сразу отрисованным без анимации штриховки (`stroke-dashoffset`).
5. **Логика и функционал остаются на 100% идентичными.**

## 8. Результаты аудита (Motion Debt)

В ходе детального исследования кодовой базы выявлены следующие разрывы непрерывности (Motion Debt):

1. **Маршрутизация (Route Transitions):**
   *Проблема:* Смена экранов в React Router происходит через моментальный демонтаж/монтаж DOM. При переходе с Главной на Запись или с Тренеров в профиль тренера возникает резкий стробоскопический скачок.
2. **Связь «Слот → Подтверждение записи»:**
   *Проблема:* На экране `/schedule` карточка слота содержит интервал `18:00–19:00`, статус и загрузку. При тапе открывается экран `/booking/:id`, где эти же данные рисуются в другом месте с нуля. Теряется ментальная модель того, что пользователь подтверждает именно выбранный слот.
3. **Связь «Список тренеров → Профиль тренера»:**
   *Проблема:* Аватар тренера, его имя и теги специализаций мгновенно исчезают и появляются заново в шапке `TrainerPage` без геометрической преемственности.
4. **График и метрики на странице Прогресса:**
   *Проблема:* На странице `/progress` число веса (`78.4 кг`) и SVG-график появляются статично без фазы сборки, создавая ощущение неотзывчивого табличного интерфейса.
5. **Модальные окна и Toast:**
   *Проблема:* `Toast` и модальные окна (`AddMeasurementModal`, `HealthSourcesModal`, `CancelConfirmModal`) монтируются и размонтируются без плавной физичной шторки или подъема карточки.
6. **Выбор формата тренировки:**
   *Проблема:* Radio-кнопки «Самостоятельно» / «С тренером» переключают рамку и галочку без микродвижения радио-индикатора.

## 9. Выбранная технологическая основа

Для достижения кинематографичного эффекта без утяжеления бандла выбрана связка:

1. **Native View Transitions API + React Router 7:**
   *Позволяет браузеру аппаратно интерполировать геометрию связанных элементов между маршрутами (`view-transition-name`). При этом бандл приложения не раздувается тяжелыми библиотеками вроде Framer Motion.*
2. **Centralized CSS Motion Tokens:**
   *Чистые аппаратные CSS-переходы на `transform` и `opacity` с нулевым оверхедом рантайма.*
3. **Легковесные React Hooks:**
   - `useReducedMotion`: реактивное отслеживание системных настроек пользователя;
   - `useCountUp`: управляемая дискретная сборка чисел с аппаратным таймингом `requestAnimationFrame` и защитой от перерисовки при reduced-motion;
   - `safeStartViewTransition`: безопасная обертка для View Transitions с graceful fallback.

## 10. Три целевых демонстрационных сценария (Showcase Flows)

Для следующего этапа реализации выбраны 3 самых показательных сценария:

1. **Сценарий 1: Выбор слота времени → Экран подтверждения записи (`/schedule` → `/booking/:id`)**
   - Блок времени (`18:00–19:00`) и карточка слота пространственно трансформируются в заголовок экрана подтверждения.
   - Физический отклик выбора формата тренировки (radio toggle).
   - Трансформация кнопки «Подтвердить запись» в состояние успешного подтверждения с фиксацией статуса.

2. **Сценарий 2: Карточка тренера → Профиль тренера (`/trainers` → `/trainers/:id`)**
   - Плавная морф-интерполяция аватара тренера из компактной карточки в Hero-шапку.
   - Разворачивание тегов специализаций и описания без скачка высоты контейнера.

3. **Сценарий 3: Экран прогресса и сборка данных (`/progress`)**
   - Кинематографичная сборка ключевого числа веса (count-up с атлетичным замедлением).
   - Плавная отрисовка линии SVG-графика (`stroke-dashoffset`) от базовой линии к точкам замеров.
   - Микро-реакция всплывающего тултипа при касании точек графика.

## 11. Системные микроинтерфейсы и тактильный отклик (Microinteractions & Haptics)

Микроинтерфейсы в «Железном Рюрике» подчинены правилу: **не анимировать всё подряд**, а давать осязаемый тактильный отклик и объяснять переход между состояниями.

### 11.1. Buttons & CTA
- **Touch Down:** Небольшая упругая компрессия (`transform: scale(0.975)`), без отскока, длительность 90–120ms (`--motion-duration-micro-fast`, кривая `--motion-ease-direct`).
- **Release:** Контролируемый возврат в исходное состояние без «желейных» колебаний.
- **Подтверждение записи:** Кнопка не исчезает и не заменяется модальным окном — она переходит в фазу выполнения (`.button--submitting`), где легкая полоса прогресса сигнализирует о записи, после чего фиксируется в зеленый атлетичный бейдж подтверждения (`.button--confirmed`, «✓ Запись подтверждена») с тактильным откликом `haptics.success()`.

### 11.2. Selection States (Формат тренировки & Тренеры)
- **Tap Compression:** При тапе по карточке выбора (`.booking-option`) происходит микровжатие (`--motion-card-press-scale`).
- **Selection Marker:** Окружность радио-метки плавно окрашивается в желтый цвет (`var(--brand-yellow)`), а иконка галочки плавно масштабируется (`checkmarkDrawIn` 180ms `--motion-ease-emphasized`), исключая резкие стробоскопические скачки.
- **Haptic:** Вызов `haptics.selection()`.

### 11.3. Date Picker Sliding Surface (`DateStrip`)
- Вместо исчезновения и появления желтого фона на новой дате, плашка выбора (`.date-strip__selection-surface`) физически скользит по горизонтали между днями недели за 220ms (`--motion-ease-emphasized`).
- Касание новой даты сопровождается тактильным `haptics.selection()`.

### 11.4. Capacity Indicator (Загрузка зала)
- **Digit Flip:** Смена числа занятых мест (`.capacity-digit-flip`) сопровождается вертикальным микродвижением цифры с кривой `--motion-ease-enter`.
- **Сегменты шкалы:** 8 дискретных атлетичных блоков плавно обновляют заливку за 180ms без агрессивных вспышек цвета.

### 11.5. Toggles & Switches
- **Физика тумблера:** Сдвиг ползунка с микровжатием/микрорастяжением (`width: 22px`) во время касания пальцем (`:active`), мягкое перетекание цвета подложки (`var(--brand-yellow)` / `#23272E`).
- Без пружинистого желе и овершутов.

### 11.6. Press States
- Все кликабельные карточки и интерактивные строки (`.time-slot.is-available`, `.settings-row`, `.trainer-card__header`, `.main-card--booked`) обладают легким scale down (`0.98–0.99`) через служебный класс `.motion-pressable` и токены движения, гарантируя нулевое смещение окружающего layout-потока.

### 11.7. Haptics Architecture (`@capacitor/haptics`)
- Централизованный сервис `src/services/haptics.ts`:
  - `haptics.selection()`: легкий дискретный клик при выборе дат, radio-кнопок, тумблеров.
  - `haptics.light()`: тактильный отклик на нажатие вторичных действий и свайп.
  - `haptics.success()`: подтверждение успешной записи или синхронизации данных.
  - `haptics.warning()`: предупреждение при отмене записи или выходе из аккаунта.
- Автоматически проверяет `Capacitor.isNativePlatform()`, оставаясь абсолютно бесшумным и безопасным no-op в браузере без назойливых браузерных вибраций.

## 12. Экран «Мой прогресс» (Data-Driven Motion Design)

Экран прогресса — главное data-driven пространство приложения. Движение здесь объясняет изменение данных и масштаба, даёт тактильный отклик и сохраняет пространственную стабильность (Spatial Stability), не превращаясь в перегруженный дашборд.

### 12.1. Hero Metric (Число веса)
- **Мягкий числовой переход:** Значение интерполируется от `previousKnownValue` к `currentValue` за 380ms (`--motion-ease-emphasized`).
- **Запрет счета от нуля:** При первой загрузке или отсутствии сохраненного значения в `sessionStorage` число отображается сразу без рулетки от 0.
- **Стабильность при повторном открытии:** При возврате на экран без изменения данных пересчет не запускается повторно.

### 12.2. Delta (`−1,3 кг`)
- Появляется с мягкой задержкой в 120ms (`.metric-change--reveal`) после основного значения с кривой `--motion-ease-enter`.
- Никаких пульсаций, мерцаний или цветных ореолов.

### 12.3. Линия и точки графика (`ProgressLineChart`)
- **Первичная отрисовка:** Линия аккуратно чертится слева направо (`stroke-dashoffset: 700 → 0`, 600ms `--motion-ease-emphasized`), точки появляются последовательно вслед за фронтом штриха.
- **Защита от повтора:** Флаг `hasDrawnRef` предотвращает повтор анимации входа при скролле страницы или мелких перерендерах.

### 12.4. Переключение периодов (`7д → 30д → 3м → 1г`)
- **Скользящая плашка выбора:** `.chart-period__surface` непрерывно скользит между кнопками табов за 220ms.
- **Морфинг геометрии линии:** Линия интерполирует свою форму через 32 равномерных узла в `requestAnimationFrame` за 340ms, создавая ощущение непрерывного масштабирования единого датасета вместо резкого исчезновения/появления.
- **Координаты точек:** Элементы `<circle>` плавно перемещаются к новым позициям `(cx, cy)` через аппаратные CSS-переходы.
- **Подписи дат:** Мягкий кроссфейд граничных дат (`.line-chart__labels--crossfade`).

### 12.5. Интерактивный тултип и гайдлайн
- При тапе по точке:
  - Точка деликатно увеличивается с $r=3.5$ до $r=5.5$.
  - Отображается вертикальная пунктирная направляющая (`.line-chart__guide`).
  - Тултип центрируется над точкой.
- При скольжении/переключении между точками тултип **не исчезает**, а непрерывно перемещается через `translate3d(x, y, 0)`, сохраняя контекст атлета.
- Вызов `haptics.selection()` при каждом выборе точки.

### 12.6. Синхронизация здоровья (Health Sync)
- В модальном окне `HealthSourcesModal`:
  - Вместо блокирующего спиннера в строке источника появляется тонкая полоса прогресса (`.source-item__sync-bar`), а подпись меняется на `«Синхронизация…»`.
  - По завершении статус мягко меняется на `«Обновлено только что»` (`.source-item__synced-note`) с тактильным откликом `haptics.success()`.
  - При поступлении новых замеров экран `ProgressPage` мягко трансформирует hero-значение и достраивает новую точку на графике без перезагрузки интерфейса.

### 12.7. Section Reveal
- При первой загрузке первый вьюпорт собирается единым мягким каскадом:
  - Сводка визитов и недель (`0ms`);
  - Карточка веса и график (`60ms`);
  - Дополнительные показатели (`120ms`).

## 13. Главный экран (Launch Choreography & Live State Transitions)

Главный экран задает первое впечатление от приложения: строгий, живой и функциональный спортивный интерфейс без рекламного шума, 3D-графики, интро-видео или блокирующих заставок.

### 13.1. Семантический порядок запуска (Semantic Order Choreography)
После нативного сплеша системный shell (нижняя навигация и шапка) отображаются сразу. Контент первого вьюпорта проявляется в строгом смысловом порядке с совокупной длительностью до 540ms:
1. **0ms (`.home-launch-step-1`):** Приветствие атлета и бейдж клуба;
2. **80ms (`.home-launch-step-2`):** Время ближайшей тренировки (`.main-card__time-row`);
3. **140ms (`.home-launch-step-3`):** Название тренировки, тренер и тайминг (`.main-card__info`);
4. **200ms (`.home-launch-step-4`):** Главный CTA («Записаться» / «Вы записаны» / «Найти время»);
5. **260ms (`.home-launch-step-5`):** Виджет текущей загрузки зала;
6. **320ms (`.home-launch-step-6`):** Блок новостей зала.

Интерфейс остается интерактивным с первого кадра: клики по карточкам и табам не блокируются.

### 13.2. Защита от повторного воспроизведения (Session Guard)
- Статус запуска фиксируется в `sessionStorage` (`ryrik_home_launched`).
- При переключении между вкладками (Главная ↔ Расписание ↔ Прогресс) или возврате из фонового режима экран отображается статично без повтора ступенчатых задержек.
- Через 700ms после первичного входа анимационные классы удаляются из DOM, переводя компоненты в чистый статичный режим.

### 13.3. Акцентная линия Hero-карточки (`.main-card--accent-draw::before`)
- Фирменная желтая вертикальная полоса карточки отрисовывается сверху вниз (`transform-origin: top; scaleY(0) → scaleY(1)`) за 220ms с задержкой 80ms в такт появлению времени тренировки.
- Все второстепенные разделители страницы остаются статичными.

### 13.4. Hero Slot Time & Micro Digit Flip
- На старте время отображается спокойно без «счетчика от нуля».
- При обновлении слота (например, когда пользователь выбрал другое время или текущее время истекло) срабатывает сдержанный вертикальный микрофлип (`.time-digit-flip`, 180ms, `--motion-ease-enter`).
- Элемент времени наделен `viewTransitionName: 'hero-slot-time'`, связывающим карточку с экраном бронирования.

### 13.5. Индикатор загрузки зала (`CapacityIndicator`)
- Начальное состояние отображается сразу (без каскадного бега от 0).
- При живом поступлении данных (polling/SSE):
  - Цифра совершает аккуратный вертикальный сдвиг (`.capacity-digit-flip`);
  - 8 атлетических сегментов плавно переключают заливку через аппаратные CSS-переходы (180ms `--motion-ease-emphasized`);
  - При достижении 8 из 8 статус спокойно переходит в предупреждающий режим без резких вспышек.

### 13.6. Морфинг при возврате из бронирования (`hero-main-card`)
- Карточка `BookingCard` во всех состояниях (записан, свободно, мест нет, не выбрано) связана с единым transition-тегом `viewTransitionName: 'hero-main-card'`.
- При переходе из `/booking/:id` после подтверждения или отмены записи карточка плавно трансформирует свои габариты и содержимое в новое состояние в рамках View Transitions API.
